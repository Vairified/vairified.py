`client.events.list()` browses the event catalogue — what is on, near a point, within a date range. Until now the API could only describe an event you already held an id for, which helps a partner who was pushed one and nobody else. `lat`, `lng` and `radius_miles` go together: sending one or two of them is refused by the API rather than ignored, because a half-applied location filter returns events nowhere near the point given while looking like it worked, and an event with no coordinates is excluded from a radius search since it cannot be known to be within the radius. Dates match on overlap, so a multi-day event is returned when the window falls anywhere inside it. Events now carry a `location` with the venue name, address, city, state, zip and coordinates, plus `location.has_coordinates`; `latitude` and `longitude` are `None` for an event that has never been geocoded and never `0`, because zero is a real coordinate in the Gulf of Guinea and a zero fallback would cluster every un-located event on one pin in the ocean. Adds the frozen models `Event`, `EventLocation`, `EventClub` and `EventsPage`. Requires the `key:event:read` scope, which is TRUSTED-gated — the same scope as the existing per-event reads.
